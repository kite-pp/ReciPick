# 문서 관리 규칙

문서가 중복되거나 서로 다른 결론을 말하지 않도록 문서별 책임을 구분합니다.

## 문서별 역할

| 문서                     | 관리하는 내용                                | 갱신 시점                           |
| ------------------------ | -------------------------------------------- | ----------------------------------- |
| Notion 프로젝트 결정사항 | 제품 범위, 채택/제외 기술, 주요 의사결정     | 범위나 기술 결정이 바뀔 때          |
| Notion 팀 컨벤션         | 팀 공통 Git·협업 원칙                        | 협업 절차가 바뀔 때                 |
| `README.md`              | 실행 방법, 명령어, 현재 라우트와 최상위 구조 | 실행 환경이나 사용자 경로가 바뀔 때 |
| `REACT_CONVENTION.md`    | 코드, Git, 스타일 작성 규칙                  | 구현 규칙이 바뀔 때                 |
| `docs/APP_STRUCTURE.md`  | 계층별 책임과 의존 방향                      | 폴더 또는 상태 구조가 바뀔 때       |
| GitHub Issue/PR          | 작업 목적, 변경 이력, 검증 결과              | 모든 작업 단위                      |

## 단일 기준 원칙

- 제품 요구사항과 기술 채택 여부는 Notion 프로젝트 결정사항을 기준으로 합니다.
- 저장소에서 바로 검증 가능한 실행 방법과 코드 구조는 저장소 문서를 기준으로 합니다.
- 작업 중 발견한 불일치는 코드만 맞추지 않고 관련 문서를 같은 PR에서 갱신합니다.
- 같은 내용을 여러 문서에 복사하기보다 기준 문서로 링크합니다.
- 더 이상 유효하지 않은 문서는 삭제하거나 상단에 폐기 상태와 대체 문서를 명시합니다.

## 작성 규칙

- 제목은 문서 목적이 드러나는 명사형으로 작성합니다.
- 한 섹션에는 하나의 주제만 담고, 긴 설명보다 규칙과 예시를 우선합니다.
- 명령어, 경로, 파일명, 코드 식별자는 코드 서식을 사용합니다.
- 날짜가 필요한 결정에는 `YYYY-MM-DD` 형식을 사용합니다.
- 예정 사항을 현재 구현처럼 표현하지 않습니다.
- 미정 사항은 담당자와 결정 조건을 함께 기록합니다.

## 변경 절차

1. GitHub Issue에 문서 변경 이유와 영향을 적습니다.
2. 실제 코드와 기준 Notion 페이지를 확인합니다.
3. 코드와 문서를 한 작업 브랜치에서 함께 수정합니다.
4. 링크, 명령어, 파일 경로가 실제로 유효한지 검증합니다.
5. PR 본문에 변경한 기준 문서와 검증 결과를 적습니다.

문서만 바꾸는 작업도 동일하게 Issue와 PR을 사용합니다.
